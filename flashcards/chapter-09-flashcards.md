## Chapter 9: Domain 10: Application Security — Flashcards

| # | Front (Question) | Back (Answer) |
|---|-----------------|---------------|
| 1 | SAST vs DAST vs SCA — what does each analyze? | SAST: source/binary code, pre-runtime (finds logic flaws like SQLi). DAST: running application, black-box, post-deploy (finds runtime/config flaws). SCA: third-party/open-source dependencies (finds known CVEs & license risk). Exam tip: SAST = 'white box, pre-build', DAST = 'black box, running app'. |
| 2 | Shift-left security — definition | Moving security testing and requirements as early as possible in the SDLC (design/code) rather than only before/after release. Exam tip: the earliest point tested is threat modeling during design, before code is written. |
| 3 | Golden rule for credentials in cloud-native app code | Never hardcode secrets in source, config files, or container images. Use a secrets manager/vault (e.g., HashiCorp Vault, AWS Secrets Manager, Azure Key Vault, GCP Secret Manager) and inject secrets at runtime. |
| 4 | Common vault services for secrets management | HashiCorp Vault, AWS Secrets Manager, Azure Key Vault, GCP Secret Manager. All support centralized storage, access policies, and automated rotation — exam tests recognizing these as the correct pattern vs. hardcoded config. |
| 5 | Artifact/build signing purpose in CI/CD | Cryptographically signs build outputs (e.g., container images) so their provenance and integrity can be verified before deployment, preventing tampered or substituted artifacts from running in production (e.g., Sigstore/cosign). |
| 6 | Pipeline access control best practice | Separate duties: code-contribution rights ≠ pipeline/deployment configuration rights. Require approval to change pipeline definitions/build scripts, apply least privilege to CI/CD service accounts and secrets. |
| 7 | git-secrets / pre-commit secret scanning | Tools like git-secrets or truffleHog scan commits/pushes for patterns matching credentials (API keys, private keys) and block them before they enter the repo history. Prevents the #1 commonly-missed exam trap: 'delete the secret from the latest commit' (history still contains it). |
| 8 | cosign / Sigstore | Open-source tooling (part of the Sigstore project) used to sign and verify container images and other build artifacts, providing cryptographic proof of build integrity in a CI/CD pipeline. |
| 9 | OWASP API Security Top 10 — how many categories? | 10 categories (2023 edition). Exam tip: know that BOLA (Broken Object Level Authorization) is ranked #1 — the most tested API vulnerability in cloud security exams. |
| 10 | BOLA (Broken Object Level Authorization) | API1:2023 in OWASP API Security Top 10. Occurs when an API fails to verify the requesting user is authorized to access the specific object/resource ID requested. Fix: enforce per-object authorization checks server-side, not just authentication. |
| 11 | Immutable infrastructure pattern | Servers/containers are never modified in place after deployment — updates are done by building and deploying a new signed artifact/image, then destroying the old one. Reduces configuration drift and unauthorized runtime tampering, supports build-integrity verification. |
| 12 | Secure SDLC for cloud-native apps — key adaptation vs traditional SDLC | Adds automated, pipeline-embedded controls (SAST/DAST/SCA/secrets scanning/IaC scanning) at every commit/build rather than periodic manual security reviews, reflecting continuous deployment cadence of cloud-native development. |
